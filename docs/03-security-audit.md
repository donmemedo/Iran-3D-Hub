**Severity** is assigned by this audit from reachability and impact. CVSS was not computed. HANDOFF's groups (Critical and high, Medium, Low and info) were the starting point. The "Critical and high" group is split by impact, item 9 is split into a login row and a register row, and one HANDOFF Medium item, the zero-bounding-box crash, is rated Low because it is an unauthenticated 500 with no lasting effect.

| Severity | Meaning here |
|---|---|
| Critical | Remote, cheap, and ends in account forgery or code execution |
| High | A visitor or customer gets goods, data or an outage the business did not intend, with little effort, or a published default credential exists |
| Medium | Needs a precondition or has limited reach: hardening gaps with a real path, bounded data exposure |
| Low | Defence in depth, correctness, UX or reliability defects |
| Info | Hygiene |

## 5. Caveats and discrepancies found while writing this register

These are places where a claim is narrower than it looks. None was changed in the code.

1. `test_hub_detail_404_and_cancel_rules` tests only the hub 404 and 200 (`backend/tests/test_security.py:215-217`). The cancel rules (`too_late_to_cancel`) and the compare-and-set path (`409 order_changed`, `orders.py:98-107`) have no test. The cross-user cancel result comes from the live probe only.
2. Two of the 50 tests passed on the original code (`test_quote_token_cannot_be_used_as_auth_token`, `test_price_is_never_negative_or_zero`). They are guards, not evidence of a finding. The negative-quantity finding is proved by the parametrised `test_manual_quote_rejects_bad_input`.
3. The final result (60 of 60 pass) is recorded in `docs/evidence/final-test-run.txt`.
4. The original login timing (232.7 ms known against 6.8 ms unknown) is quoted from the HANDOFF finder run; the raw output is not in `docs/evidence/`.
5. `evidence/live-probe-result.json` records no host, commit, timestamp or response status for the two timing requests, so the explanation of its one failing check is an inference from the code path (see `04-penetration-test.md`).

7. Several fixes have no test at all: demo account opt-in, extension allow-list, validation-error echo, reviewer privacy, the whole frontend. They are covered by code reading, and in two cases by a probe check.
8. `security.py:131-140` (`optional_user`) is now unused. It is harmless, but dead auth code is worth deleting.
9. The comment at `security.py:19` calls scrypt N=2^15, r=8, p=1 "OWASP's recommended minimum". The current OWASP cheat sheet, as recalled and not re-checked while writing this, lists N=2^15 together with p=3, or N=2^17 with p=1, as equal-cost minimums, so the parameters are at the low end (SEC-71). The memory cap on concurrent hashes explains the choice, but the comment overstates it.

## 6. Residual risk and accepted trade-offs

Each line is something a reader should assume is still true after this pass.

| # | Residual risk | Why it stays | What closes it | Rows |
|---|---|---|---|---|
| 1 | The login token lives in `localStorage` | Script running in the page can read it, and it stays valid for its 24 h lifetime because there is no revocation. A cookie session needs a CSRF design and same-site hosting of the API. No data-bearing XSS sink was found; the only `dangerouslySetInnerHTML` is a constant string | HttpOnly SameSite cookie with CSRF protection, or short access token plus a refresh token backed by a session table | SEC-38, SEC-28 |
| 2 | CSP keeps `script-src 'unsafe-inline'` | Next.js App Router emits inline bootstrap scripts and the theme script must run before first paint (`frontend/next.config.ts:14-21`). The CSP is therefore a weak backstop against an injected inline script | Per-request nonce with `strict-dynamic`, which gives up static prerendering (the config comment says so) | SEC-36 |
| 3 | The rate limiter is in-process | Counters are per uvicorn worker (compose runs one), so scaling out multiplies every limit. The prune only removes expired keys, so memory is bounded by distinct clients in the window, not by a hard cap. Check and record are separate steps (`auth.py:41`, `:50`) | nginx `limit_req` or shared counters in Redis | SEC-77 |
| 4 | Login and register are limited per IP | Everyone behind one NAT shares one bucket of 10 attempts per minute. With `FORWARDED_ALLOW_IPS` too wide a client can spoof its address; too narrow and all users share the proxy's bucket. Ten failures lock one email for 10 minutes, so a known email can be locked out | Per-account plus per-IP policy, device cookie or CAPTCHA, correct proxy settings | SEC-77, SEC-78 |
| 5 | Only an admin can advance orders | The `hub` role exists but `Hub` has no owner column, so producers cannot see or move their jobs. Admins operate by hand | `Hub.owner_user_id`, hub-scoped listing and transitions | SEC-82 |
| 6 | There is no payment gateway | `pending_payment` to `in_production` is an admin simulation, `commission` is computed but never collected, and the landing copy promises «پرداخت امن». Reviews depend on the admin setting `delivered` | Gateway, webhook that advances the order, copy fix | SEC-81, SEC-18 |
| 7 | No email verification and no password reset | No email channel exists. A typo or someone else's address is accepted; a forgotten password is lost | Verification token and reset flow over an email provider | SEC-83 |
| 8 | A signed quote can be ordered more than once | The token is a bearer credential, valid 24 h and not single use; replay is capped by 60 orders per hour per user | Store a token id on the order with a unique constraint, or an idempotency key | SEC-61 |
| 9 | Prices rest on declared geometry | Manual volume and bounding box are typed by the customer, and a crafted mesh can understate volume. Only non-manifold, truncated and unreadable files are flagged. Control today is a human check at the hub | Verify declared against delivered size, or require inspection for manual entries | SEC-80 |
| 10 | Register still confirms whether an email exists | A generic reply would confuse honest users and there is no email channel. Bounded by the shared limit | Verification email (row 7) makes a generic reply possible | SEC-17 |
| 11 | One client can hold both parse slots | Concurrency is not per IP, so upload quoting can return 503 to everyone while manual quoting keeps working. The limiter and slot cap run after the multipart body is received, so simultaneous 60 MiB uploads are bounded only by the 128 MB `/tmp` tmpfs and the memory limit (framework order, not tested). Parse time at the 250,000-triangle cap and the memory of two such parses against the 512 MB limit were not measured | Per-IP concurrency, a worker process or queue, measured sizing | SEC-62, SEC-24 |
| 12 | `/api/quotes/manual` has no per-IP limit | Only the 64 KB body cap applies; each call is read-only | Add the same limiter as uploads | SEC-79 |
| 13 | `sharp` 0.34.5 is still pinned and was not re-scanned | The HANDOFF advisories were not re-read; `/_next/image` is enabled although `src/` has no `next/image` | Re-run OSV; set `images.unoptimized` or bump `sharp` | SEC-02 |
| 14 | Old databases with mixed-case emails | Lookups are lower-cased and no migration lower-cases stored rows (inferred, not run) | One-off lower-casing after a collision check | SEC-70 |
| 15 | TLS, reverse proxy, backups and encryption at rest are not in the repo | HSTS only takes effect once TLS is in front; body limits exist in the app but not at a proxy; volumetric floods and theft of the SQLite volume are deployment concerns | Deployment hardening outside this repository | SEC-24 |
| 16 | Password hashing sits at the low end of current guidance | scrypt N=2^15, r=8, p=1 with at most 4 concurrent hashes keeps memory inside a 512 MB container (`security.py:19-23`); the legacy PBKDF2 rows upgrade on login | Raise `p` or lower the concurrency cap after measuring login latency, or switch to argon2id | SEC-71 |
| 17 | Supply chain: tag-pinned images, no hashes, no signing, no recorded CI run | Actions are pinned by SHA and lockfiles are used, but base images use tags and Python installs have no `--require-hashes` | Digest pins through Dependabot or Renovate, hash-locked requirements, signing; run CI and keep the logs | SEC-84 |
